# M9.2 Result Equivalence Contract Regression Suite

## Executive conclusion

M9.2 accepts the contract semantics for independent validation. The candidate
recognized all 10 known M9.1 evaluator artifacts while falsely accepting none
of 19 projection violations, 2 semantic negatives, 7 usable non-S11
negatives, or 20 synthetic negative cases. It retained all 75 historically
correct controls. This is a provider-free regression result, not a new product
score and not an evaluator replacement.

The next milestone is **M9.3 — Versioned Result Equivalence V2 Independent
Validation**. It must use new contract cases before any adoption decision.

## Existing evaluator V1

`evaluation.metrics.assess_query_results` remains unchanged. V1 ignores
column names and aliases, compares columns by ordinal position, requires equal
width, ignores row order by default, preserves duplicate multiplicity, and
canonicalizes NULL/date values. Numeric values use `math.isclose` with
relative and absolute tolerance `1e-6`. Extra and missing columns are rejected.
Ordered comparisons remain available for order-sensitive cases. There is no
deduplication, grain normalization, value rewriting, or SQL-shape correctness
rule.

M9.1 showed why a narrower contract is needed: 44/75 correct controls had
alias/label differences, 17/75 had SELECT/column-order differences, and zero
correct controls had projection-width differences. Thus aliases and SQL
projection syntax are not sufficient semantic identity, while extra output is
not generally harmless.

## Contract semantics

The evaluation-only version is `result-equivalence-contract-v1`; the candidate
comparator is `m92-result-equivalence-candidate-v1`. A contract declares
semantic `ResultSlot`s (dimension, measure, entity ID, display label, or
auxiliary), required slots, row-identity slots, required measures, scalar or
tabular shape, row-order policy, duplicate preservation, and either forbidden
extras or explicitly declared optional extras.

Generated and reference columns are connected to slots by frozen
evaluation-oracle annotations. These bindings are not generated by an LLM,
not inferred from values, and not an automatic runtime resolver.

An optional extra is ignored only when it is explicitly declared, required
rows and values remain identical, row cardinality and identity do not change,
and no deduplication, re-aggregation, value transformation, or subset search
is needed. Missing required slots, wrong semantic slots, wrong values, wrong
grain, duplicates, scalar/tabular changes, and undeclared business output are
rejected. Column order and aliases do not matter when semantic bindings are
unchanged; row order matters when the contract requires it.

The candidate outcomes are `STRICT_EQUIVALENT`, `CONTRACT_EQUIVALENT`,
`NOT_EQUIVALENT`, `CONTRACT_INVALID`, and `UNDETERMINED`. Contract-equivalent
acceptance emits a bounded reason such as
`DECLARED_OPTIONAL_EXTRA_IGNORED`.

The 10 artifacts split across DEV/HOLDOUT as 8/2 and were recovered 8/8 and
2/2. The 19 projection negatives remain rejected for undeclared business
output, missing required output, or wrong semantic output. The candidate
accepted 14 cases by declared optional-extra semantics and 81 by strict
equivalence; the remaining 48 were rejected (one invalid ambiguous binding
and 47 non-equivalent). The V1/candidate matrix is:

| REJECT / ACCEPT | 11 |

The matrix includes synthetic cases; it is diagnostic only. Historical
artifacts account for the intended V1-reject/candidate-accept hardening, while
the synthetic cases exercise the same boundary conditions independently of
historical labels.

The synthetic suite covers optional IDs, undeclared fields, missing fields,
wrong values and slots, expanded grain, duplicates, scalar/tabular mismatch,
ordering, aliases, NULL, numeric tolerance, multiple references, and
ambiguous bindings. It passed 30/30. In particular, the comparator never
deduplicates, re-aggregates, rewrites values, enumerates arbitrary subsets, or
uses case IDs or question strings.

## M2.8 reconciliation

M2.8 is found and remains rejected. It used a provider-generated untrusted
`ResultShapeProposal` containing outputs, shape, limit, and ordering guidance;
the 48-case development screen was neutral at 16/48, required-output recall
was 27.08%, five additional execution/contract failures appeared, and
end-to-end generation latency roughly doubled. It had no holdout.

M9.2 is materially narrower: a deterministic, server/evaluation-owned
semantic contract is bound offline to frozen results; it has no provider DTO,
prompt change, runtime validation gate, SQL generation, or runtime result
normalization. The reconciliation is therefore
`NARROWER_NEW_HYPOTHESIS_SUPPORTED_BY_NEW_EVIDENCE`, not a ResultShape revival.

## Limitations and decision

The historical portion is a regression validation suite whose semantic slot
bindings were derived from the same M9.1 cases that motivated the contract.
It demonstrates coherent safety semantics, not general evaluator correctness.
It does not establish automatic runtime slot binding, universal SQL
equivalence, or public benchmark compatibility. Projection-width relaxation
is supported only for explicitly declared optional slots; the zero width
difference among correct historical controls does not justify an
`ALLOW_ALL_EXTRA_COLUMNS` rule.

All frozen safety gates passed: 10/10 artifact recovery, zero false accepts in
all negative sets, 75/75 controls, 30/30 synthetic cases, duplicate and
wrong-grain rejection, missing-field rejection, wrong-value rejection, and
deterministic repeated execution. M1, M3, M4, routing, prompts, runtime
defaults, and the historical evaluator were not changed. Provider calls,
SQL-generation calls, repairs, judges, embeddings, rerankers, and database
executions were all zero.

M9.3 should build independent contract cases, compare V1 and V2 side by side,
and preserve versioned historical meanings before any evaluator adoption.
