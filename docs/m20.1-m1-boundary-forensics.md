# M20.1 — M1 Boundary Forensics

Status: `M20_1_M1_BOUNDARY_FORENSICS_COMPLETED`

## Objective

M20.1 analyzes the frozen M20 direct-SQL candidates before any benchmark
optimization. It determines whether the 299 cases that did not pass the M1
boundary were intentional production protection, false positives, or
implementation defects. No provider was called and no generated SQL was
regenerated.

## Frozen evidence

The analysis consumed M20 checkpoint `8439b1e10bb53dbf58b7d78a81418da33f18ca58`
and manifest hash
`36e53850a704049cdf48453f8f3910eefeb877c9c57c342c0913674c8f13025a`.
The frozen M20 case, result, and manifest files were not modified. The complete
machine-readable case ledger is
`evaluation/fixtures/m20_1_m1_boundary_forensics.json`.

M20 accounting was verified as 774 cases: 475 accepted, 264 policy rejections,
and 35 planning errors. The artifact accounts for all 299 failures exactly
once, with no accepted case included.

## Method

Each frozen generated SQL candidate was replayed through the existing M1 parser,
AST policy, EXPLAIN cost gate, and typed planning boundary. The 35 planning
errors were additionally traced to the earliest existing sub-stage. Diagnostic
execution was conservative and isolated: only parseable read-only SELECTs
without obvious unsafe operations/functions were sent to the benchmark's
read-only evaluators. Unsafe or ambiguous cases were marked
`NOT_ATTEMPTED_SAFETY`.

Gold SQL/results were used only offline to compare a safely executed frozen
candidate. They did not define M1 safety and did not change the M20 score.

## Planning errors — all 35 cases

| Root mechanism | Count | Benchmarks | Contract classification |
|---|---:|---|---|
| `EXPLAIN_PERCENT_PLACEHOLDER_COLLISION` | 35 | BIRD 15; Classic 15; Advanced 5 | Implementation defect |

Every one contained a percent-bearing SQL literal or operator. M1's
`QueryCostGate.explain()` submits `EXPLAIN (FORMAT JSON) {sql}` through
`exec_driver_sql`; psycopg interprets percent characters in the embedded query
as placeholders before PostgreSQL can explain it. This is an implementation
failure in `app/execution/cost.py`, not a semantic or safety decision.

## Root causes and intervention ranking

1. `EXPLAIN_PERCENT_PLACEHOLDER_COLLISION` — 35 cases across all three
   benchmarks; implementation defect; 25 would have been benchmark-correct in
   safe diagnostic execution. The relevant path is
   `app/execution/cost.py:QueryCostGate.explain`. This is the one recommended
   next intervention: make EXPLAIN submission literal/parameter-safe while
   preserving the existing read-only EXPLAIN and cost policy. Safety risk is
   low if the cost gate and transaction boundary remain unchanged; regression
   surface is the cost-gate adapter and its percent-literal tests.
2. `FORBIDDEN_FUNCTION` — 227 legitimate policy outcomes. Expanding the
   analytical function allowlist would be a policy change, not a forensic fix;
   the artifact does not justify it.
3. `FORBIDDEN_TABLE`, `UNKNOWN_COLUMN`, `UNKNOWN_TABLE`, and
   `QUERY_TOO_EXPENSIVE` — 37 legitimate policy outcomes in total. Changing
   object scope, catalog permissions, or thresholds requires a separate safety
   and product-policy decision. The cost bound is not relaxed from benchmark
   evidence.

## Recommended next intervention

Exactly one intervention is recommended:

> Repair the percent-placeholder collision in `QueryCostGate.explain()` with a
> deterministic driver-safe EXPLAIN submission, without changing M1 policy
> limits, object/function allowlists, or execution authority.

This recommendation addresses an independently observed implementation defect,
not benchmark correctness directly. M20.1 does not implement it.

## Non-recommendations

M20.1 does not recommend relaxing `max_plan_cost`/`max_plan_rows`, expanding the
function or object allowlists, changing M1 thresholds, modifying prompts,
regenerating SQL, adding QueryPlan/Window routing, adding memory, or starting
semantic mismatch analysis. Those changes are not justified by this boundary
evidence.

## Integrity and limitations

- Provider calls: 0.
- M20 case/result/manifest artifacts remain immutable.
- All 299 M1 failures are accounted for exactly once.
- Planning errors plus policy rejections equal 299.
- Diagnostic execution was read-only and conservative; nine cases were not
  attempted for safety.
- This is boundary forensics, not a full semantic failure taxonomy.
- The next analysis milestone may use this artifact to test the one selected
  cost-gate fix; it must not silently rewrite M20.
