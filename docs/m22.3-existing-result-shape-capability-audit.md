# M22.3 Existing ResultShape Capability Audit

## Why this audit was necessary

M22.2 found a refined projection population, including six
`EXTRA_PROJECTED_COLUMN` and two `MISSING_PROJECTED_COLUMN` cases. M22.3 audits
the ResultShape capability that already exists in the repository before any
new output contract is considered. It does not add a contract or change the
production path.

This audit used the current repository HEAD
`98a7473660b7087b86abe0ceeaf5792a8b19b920`, M20 manifest
`36e53850a704049cdf48453f8f3910eefeb877c9c57c342c0913674c8f13025a`, and the
immutable M22.2 artifact hash
`99d9c1bf9fce30275e3de86af767427ba64dd2bc096ac4229e9b568354ecac74`.

No provider calls, fresh generation, benchmark run, or production behavior
change occurred.

## Existing contract

The implementation is in `app/generation/result_shape.py`.

`ResultShapeProposal` contains:

```text
outputs: 1..32 ResultShapeOutput values
shape: ROW_FILTER | AGGREGATE | GROUPED_AGGREGATE | GROUPED_TOP_K |
       RATIO | WINDOW | OTHER
explicit_limit: optional integer 1..1000
explicit_order_direction: optional ASC or DESC
optional provider/model/token/latency metadata
```

Each `ResultShapeOutput` contains a required `semantic_label`, a kind of
`PHYSICAL_COLUMN` or `DERIVED_VALUE`, and an optional `source_hint`.

The proposal is frozen and untrusted. It contains no table authorization,
join authority, filter authority, formulas, or execution permissions.

`validate_result_shape()` parses PostgreSQL SQL with SQLGlot and checks:

- output arity;
- positional physical-column source hints, including table aliases;
- optional explicit limit;
- optional order direction.

It returns the existing `ProjectionStatus` values including `EXACT`, `EXTRA`,
`MISSING`, `WRONG`, `DERIVED_EXPRESSION_MISMATCH`, and `UNCERTAIN`. In the
current implementation, `DERIVED_VALUE` is accepted by arity and does not
receive expression-level comparison. Aggregate function, DISTINCT, and
derived-expression semantics are therefore not covered. Output aliases are
ignored; physical output matching is positional.

## Production wiring

The normal path is:

```text
QUESTION
  |
  +--> TextToSqlService.run
  |       -> _run(result_shape_contract=False)
  |       -> direct SQL provider call
  |       -> M1
  |       -> execution
  |
  +--> existing ResultShape components
          -> explicit run_result_shape_contract()
          -> propose_result_shape()
          -> propose_sql(..., result_shape=proposal)
          -> M1 plan
          -> validate_result_shape()
          -> execution
```

The first branch is `PRODUCTION_ACTIVE`. The ResultShape branch is
`EXPERIMENT_ONLY` and `AVAILABLE_BUT_UNWIRED` for the current DIRECT default.
`validate_result_shape()` is invoked only after M1 planning and before
execution when the explicit result-shape branch is selected. The current
DIRECT runtime does not construct a ResultShape proposal.

## Target population and method

M22.2 native projection cases and M22.1 reassigned projection cases were
reconstructed and deduplicated. The M22.3 intervention family was then
restricted exactly as specified:

| Source | Count |
|---|---:|
| M20.2 native projection | 3 |
| M22.1 projection-causal | 15 |
| overlap | 0 |
| unique M22.2 candidates | 18 |
| selected EXTRA projected column | 6 |
| selected MISSING projected column | 2 |
| M22.3 target | 8 |

The frozen M20 generated SQL was checked by hash. Reference SQL was used only
offline, from the bounded, hash-verified M22.2 reference representation, to
construct evaluator-only proposals and AST-aware projection counterfactuals.

For each target, the minimal proposal was built from the reference output
arity and physical output hints. Non-physical outputs use the existing
`DERIVED_VALUE` kind. The proposal was not added to runtime or sent to a
provider.

## Representability and validator detection

All eight target cases are `REPRESENTABLE_AS_IS`: the existing contract can
express their required output count and physical/derived output descriptors
without expansion.

The unchanged validator produced the following results on the frozen wrong
SQL:

| Expected causal family | Count | Validator result | Detected |
|---|---:|---|---:|
| extra output | 6 | `PROJECTION_EXTRA` | 6 |
| missing output | 2 | `PROJECTION_MISSING` | 2 |
| total | 8 | rejected | 8 |

For each case, only the SELECT expressions were replaced with the reference
expressions using a SQLGlot AST operation while retaining the generated query
structure. The unchanged validator accepted all eight corrected projection
queries with `PROJECTION_EXACT`.

This proves a bounded detection capability for output presence on this
population. It does not prove that a provider can reliably infer a proposal,
nor that ResultShape improves end-to-end correctness.

## Correct-case false-positive control

A deterministic control used old M20 `ALLOWED` and correct cases, selecting one
BIRD and one Defog case for every available physical projection bucket:

```text
NO_JOIN_SINGLE_PHYSICAL
NO_JOIN_MULTI_PHYSICAL
ONE_JOIN_SINGLE_PHYSICAL
ONE_JOIN_MULTI_PHYSICAL
MULTI_JOIN_SINGLE_PHYSICAL
MULTI_JOIN_MULTI_PHYSICAL
```

This produced 12 controls spanning BIRD and Defog, with single/multiple
physical projections and no/one/multiple joins. A proposal derived from each
control's own frozen physical projection was accepted in all 12 cases; there
were zero false rejects and zero uncertain results. This is validator
regression-surface evidence, not a new benchmark score.

## Alias and output order

The validator accepts `SELECT c.name AS display_name FROM customers AS c` for a
physical `customers.name` source hint. SQL table aliases are resolved and
output aliases are ignored.

Physical output matching is positional. A proposal for `[items.a, items.b]`
rejects `SELECT b, a FROM items` as `PROJECTION_WRONG`. This is deterministic
and useful for an explicit output contract, but it is not a separate semantic
ordering model. M22.2 had no causal output-order cases.

## Derived, aggregate, and DISTINCT boundary

The existing validator is physical-column-aware but not expression-semantics
aware. With a `DERIVED_VALUE` proposal, the current validator accepts each of
the following one-column expressions by arity:

```text
SUM(amount)
AVG(amount)
COUNT(DISTINCT customer_id)
```

Consequently it does not distinguish aggregate function, aggregate target,
derived expression, or DISTINCT semantics. These boundaries are outside the
selected eight-case intervention family and must not be claimed by M23.

## QueryIntent overlap

The selected population contains seven cases for which existing QueryIntent
fields can carry equivalent direct output-field information, and one partial
case (`defog_classic:classic:31`) involving a derived aggregate output:

| Classification | Count |
|---|---:|
| `QUERYINTENT_HAS_EQUIVALENT_INFORMATION` | 7 |
| `QUERYINTENT_PARTIAL` | 1 |
| `RESULTSHAPE_ADDS_DISTINCT_INFORMATION` | 0 |

ResultShape is therefore not uniformly new information. Its distinct value
for this audit is its narrower output-shape validation and generation guidance,
not a new source of schema or aggregate authority.

## Historical M2.8 evidence

The repository contains the historical implementation in
`evaluation/run_m28.py` and its development report in
`docs/m28-result-shape-ablation.md`. The 48-case development screen used the
same `gpt-5.6-luna` model and found:

```text
baseline result equivalence:       16/48
ResultShape result equivalence:    16/48
extra projection rate:             37.50% -> 0.00%
required-output recall:             27.08%
provider calls:                     48 -> 95
average end-to-end latency:         1316 ms -> 2618 ms
holdout:                            none
```

That result rejected a broad production promotion. It does not invalidate
the narrower M22.3 finding that the existing contract is technically testable
for the eight confirmed missing/extra-output cases.

## Decision and M23 boundary

Decision:

```text
EXISTING_RESULTSHAPE_SUFFICIENT_FOR_M23
```

The decision is limited to authorizing a bounded experiment. It is not a
production integration decision. The evidence is:

1. the target population is exactly six extra and two missing outputs;
2. all eight are expressible without changing the frozen contract;
3. the unchanged validator detects all eight frozen wrong projections;
4. the AST-corrected projection controls are accepted in all eight cases; and
5. the bounded correct controls show no validator false rejects.

The proposed next experiment is:

```text
CONTROL:      current DIRECT generation
INTERVENTION: existing propose_result_shape()
              -> existing result-shape guidance
              -> SQL
              -> unchanged M1
              -> execution/evaluator
```

It should use fresh internal/holdout cases plus a small targeted public
missing/extra projection slice, and measure correctness, missing/extra rate,
M1, execution, regressions, ResultShape validity, provider calls, latency, and
tokens. It must not add a new contract, router, repair, judge, best-of-N, or
full 774-case rerun.

No production default was changed and no ResultShape contract was expanded in
M22.3.
