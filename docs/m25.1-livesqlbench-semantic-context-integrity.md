# M25.1 — LiveSQLBench semantic context integrity

## Why this audit exists

M25 was a valid one-call DIRECT pilot, but its 1/18 result was based on the
exact context supplied at that time. M25 passed the protected
`external_knowledge` field through as integer references. This audit checks
whether those references were the semantic knowledge itself and compares that
input surface with the official direct baseline.

M25 remains immutable evidence: 18 cases, 18 calls, and 1/18 official raw
correct. M25.1 does not rerun or reinterpret its score.

## Official baseline context

The frozen upstream source is commit
`e15cd221267e06fabfaf6a3d4a69308280ce9a7c` of the
[LiveSQLBench repository](https://github.com/bird-bench/livesqlbench). Its
`baseline/src/prompt_generator.py` loads, per database, the static schema,
column-meaning JSON, and KB JSONL. Its prompt template then exposes the schema,
all column meanings, and the full KB records (the visible KB fields are
`id`, `knowledge`, `description`, and `definition`). The baseline indexes KB
records by knowledge name and does not use the protected per-case reference
list to filter the prompt. This is the static direct baseline, not Agent mode.

## M25 actual model-visible context

The protected M25 model-I/O journal and the unchanged Decision-SQL provider
path show that every pilot request contained the question, the live structural
schema context, and an `OFFICIAL EXTERNAL KNOWLEDGE` block containing the raw
integer reference list. The request did not contain resolved KB descriptions or
definitions, official column meanings, gold SQL, or test cases. This was
verified from captured serialized contexts and messages, not inferred from
variable names.

Thus M25's `18/18 external knowledge coverage` meant that the protected field
was present, not that its referenced semantic records were model-visible.

## Resource inventory and resolution

All 18 database directories contain the expected public schema, column-meaning,
and KB resources. Across the resources there are 2,286 physical columns and
2,286 meaning entries. 2,284 meaning keys match live physical columns; two
entries are unmatched/orphaned under the discovered `database|table|column`
key shape. There are no case-collision keys. KB resources contain 1,082 rows,
1,081 unique knowledge names, and one duplicate knowledge name in the `fake`
resource. The renderer follows the official name-indexing behavior for that
duplicate while preserving unique integer IDs for diagnostics.

The protected field is a list of integers: 603 references across the complete
270-task protected population and 454 across the 180 SELECT tasks. Exact
integer-ID resolution succeeds for all SELECT references and all 37 pilot
references, with no fuzzy matching, unresolved references, or ambiguous IDs.
The official direct context nevertheless exposes all database KB records rather
than only those references.

## Corrected context

The evaluation-only renderer preserves Decision-SQL's live, server-owned
structural schema context and appends deterministic benchmark-supplied
annotations:

```text
LIVE STRUCTURAL SCHEMA

BENCHMARK-SUPPLIED COLUMN MEANINGS

BENCHMARK-SUPPLIED EXTERNAL KNOWLEDGE
```

The annotations are context only; M1 and the live catalog remain authoritative
for tables, columns, and execution safety. No gold SQL, test cases, reference
results, or evaluator outcomes are used to select context.

The corrected context is constructable for all 180 SELECT cases and all 18
frozen pilot cases. Offline provider messages are constructable for all 18 and
contain the question and corrected context without protected evaluation fields.

## Structural schema comparison

The live PostgreSQL introspection and official static schema resources agree on
table and column sets for all 18 databases. They also agree on foreign-key
counts. The live representation carries server-owned types, nullability, keys,
and relationships; the official resource carries benchmark text formatting and
the semantic annotations are supplied separately. The corrected adapter keeps
live structural truth rather than replacing it with static text.

## Context size

For the frozen 18, approximate token counts use the deterministic planning
estimate of four characters per token. M25's captured context had median
11,343 characters / 2,836 estimated tokens, P95 17,536 / 4,384, and maximum
19,764 / 4,941. The corrected context has median 51,854 characters / 12,964
tokens, P95 66,310 / 16,578, and maximum 69,379 / 17,345.

The corrected median composition is approximately 11,302 structural-schema
characters, 17,627 column-meaning characters, and 22,115 KB characters.

## Claim boundary

M25.1 establishes a benchmark context integration defect and prepares a
corrected, deterministic, gold-safe input surface. It does not predict a new
accuracy score and does not change production prompts, M1, evaluation semantics,
or production defaults.

## Classification

`M25_1_SEMANTIC_CONTEXT_INTEGRATION_DEFECT_CONFIRMED`

## Next experiment

The existing M25 arm remains frozen at 1/18. A paired 18-case DIRECT rerun may
be considered with the same model, prompt, M1, evaluator, pilot IDs, and
one-call budget, changing only the LiveSQLBench-authorized semantic context.
