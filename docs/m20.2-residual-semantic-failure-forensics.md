# M20.2 — Residual Semantic Failure Forensics

## Objective

M20.2 explains the residual errors only after the M1 planning and read-only
execution transport defects were repaired. It uses the frozen M20-generated
SQL and its frozen evaluator outcomes to identify the earliest observable
semantic decision associated with each successfully executed mismatch. No
provider call, SQL regeneration, prompt change, or production behavior change
was made.

## Method and taxonomy

Every one of the 189 cases appears once in
`evaluation/fixtures/m20_2_residual_semantic_forensics.json`. The analysis
combines the question and legitimate benchmark evidence with the authoritative
schema, generated SQL AST facts, reference SQL/result evidence, and
type-preserving result hashes. The primary label is the earliest causal
mechanism supported by that evidence, rather than a raw SQL text difference.
Labels are forensic data only and are not runtime signals.

## Causal evidence

The largest observed mechanism was filter semantics: the generated predicate
structure or value differed while the relation graph was aligned. Schema
grounding was the largest cross-benchmark server-owned intervention surface;
relation-set differences were the earliest observed divergence in 56 cases.
Temporal mistakes affected 28 cases, generally as an incorrect date column or
boundary in a question whose result depended on time interpretation. Join
semantics affected 21 cases through a differing relationship graph or path.
The remaining categories are smaller and include aggregation/grain,
ordering/limit, string matching, projection, arithmetic, and subquery/set
differences. Representative IDs and per-case evidence are retained in the
artifact. No gold-derived rule was added to production.

## Existing capability mapping

The mapping is conservative and uses whole-request contracts:

- QueryPlan V1: 183 cases require contract expansion; 6 are only
  shape-compatible with catalog coverage unproven. No residual is confirmed as
  covered by the production QueryPlan V1 contract in this offline artifact.
- Window IR: four cases have a window shape requiring a whole-request contract
  check; 185 are not relevant. No new Window IR coverage is claimed.
- Governed Metric: zero cases are confirmed whole-request matches. Metric token
  recognition is not treated as capability coverage.
- Verified Memory: zero runtime coverage; memory was off.
- Direct SQL: all 189 were produced by the current direct path and reached
  result evaluation, but returned the wrong typed result.

## Recommended next intervention

Recommend exactly one bounded intervention: a server-owned schema/relationship
grounding intervention for the direct generation context. It affects 56
residuals across BIRD (46) and Classic (10), has the clearest cross-benchmark
catalog/context leverage, and addresses the earliest relation-selection
decision without relaxing M1 or expanding QueryPlan V1 in this milestone. The
likely benefit is partial rather than guaranteed: the cases include broader
schema/entity grounding, so the recommendation is not a claim that all 56 are
recoverable.

The main causal evidence is the repeated generated/reference relation-set
divergence. Existing server-owned schema and relationship representations are
the natural leverage point. Production rationale extends beyond benchmark
accuracy: a general direct path should ground table and relationship choices in
authoritative metadata rather than guessing identifiers. Regression risk is
context drift, incorrect catalog exposure, and join fanout. Likely future code
surface is the shared schema/context renderer and catalog adapter, in a
separate milestone; no such files were changed here.

## Non-recommendations

M20.2 does not recommend M1 threshold relaxation, policy whitelisting, QueryPlan
V2, aggregation/window expansion, prompt sweeps, benchmark-specific rules,
gold-aware routing or repair, memory/retrieval changes, or a fresh provider
benchmark run. Their evidence is either outside this forensic question or
would conflate safety, coverage, and semantic diagnosis.

## Limitations and next milestone

This is a development/public-benchmark forensic artifact, not a new benchmark
score. Repeated future tuning against these public sets would make them
development scoreboards rather than unseen generalization measurements. The
next proposed scope is a separate bounded server-owned schema/relationship
grounding intervention milestone. It must begin with a frozen contract and
fresh validation; it is not implemented here.
