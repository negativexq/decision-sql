# M62 Operator Playground

The local operator console is a thin presentation layer over the canonical
`DecisionSqlApplication`. The browser submits a natural-language question to
`POST /api/playground/query`; one provider response is admitted as a typed
production decision, and only `ANSWER` enters the existing `SqlSafetyService`.
That service owns parse, policy, authority, grain, EXPLAIN, cost, and read-only
execution decisions.

## Production path alignment

Live requests use the product-owned Candidate C decision contract and the
shared schema-context lineage:

```text
question → governed context → one typed model decision → deterministic gates → result
```

`model_decision` and `runtime_outcome` are separate facts. A model `ANSWER`
may still be rejected by execution authority or global policy. Non-`ANSWER`
decisions do not enter SQL runtime, and context/provider/admission failures do
not fabricate a model decision.

Safety replays are server-bound frozen proposals evaluated by the current
deterministic runtime without a provider call. They are visibly labelled in the
console and are never treated as live generation.

## Governed context integrity

The canonical production path converts the resolver's server-owned,
request-bounded envelope into the product-owned `GOVERNED_CONTEXT_V1` model.
Its deterministic JSON serialization explicitly includes `schema_catalog`,
`attributes`, `authorized_relationships`, `metrics`, `business_rules`,
`temporal_rules`, and the read-only `policy`. Empty governance sections remain
present so their absence is explicit. The same visible entity scope is used to
derive request-scoped execution authority; this does not broaden runtime
permissions.

The Schema page is the full **Governed Catalog**. A run detail instead exposes
the exact bounded model-visible context supplied to that request, together with
its content hash. Neither view contains rows, evaluator truth, hidden prompts,
or provider credentials.

## Trace connection semantics

Trace stages are emitted by the real application/runtime path. Planning and
execution use separate stages and therefore separate database-contact evidence:
`planning_connection` precedes `EXPLAIN` and the cost gate, while
`execution_connection` precedes read-only execution. If a model decision or
runtime gate stops the request, every downstream stage remains visible as
`SKIPPED` with a bounded reason such as `MODEL_NON_ANSWER` or
`EARLIER_RUNTIME_REJECTION`.

## Local run

With Docker available:

```bash
docker compose up --build
```

- UI: <http://localhost:3000>
- API: <http://localhost:8000>
- API health: <http://localhost:8000/api/health>

The API uses the existing PostgreSQL reader role and the existing OpenAI-
compatible provider configuration. Set `DECISION_SQL_LLM_API_KEY` in a local
environment when running live requests. Live presets use that same provider
path; safety and runtime-policy replays are deterministic local proposals and
make no provider call.

## Console surfaces

The four primary areas are Playground, Runs, Traces, and Schema. Runs are
bounded in-memory operator history and are restart-ephemeral. Trace records
are request-local, structured, and generated by runtime stage instrumentation;
the frontend does not infer stage status from HTTP status.

The Schema page is rendered from the application catalog as the Governed
Catalog. The trace stores bounded metadata only: no
provider payloads, credentials, authorization headers, evaluator truth, or raw
result rows are persisted in trace metadata. Proposed SQL is shown in the
operator result because it is the object being admitted by the deterministic
runtime.

## Demo scenarios

- Successful query: reaches EXPLAIN, cost admission, and read-only execution.
- Needs clarification: the live model can emit a typed clarification decision;
  SQL runtime is not entered.
- Unauthorized relation: a labelled safety replay proposal parses, then the request authority
  rejects it before database contact, EXPLAIN, or execution.
- Policy blocked: the global read-only SQL policy rejects the proposal.
